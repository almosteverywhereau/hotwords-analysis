# 热词统计与分析系统 - 项目综合报告

## 第一部分：系统设计文档

### 1. 需求分析

#### 1.1 项目背景
在舆情监控、直播弹幕分析等场景中，我们需要实时了解当前最热门的话题。传统的批处理方式（如每天统计一次）无法满足实时性要求，因此需要一个基于流式数据的热词统计系统。

#### 1.2 核心需求
1.  **实时处理**：系统需要持续接收带时间戳的文本流，处理延迟需尽可能低。
2.  **滑动窗口**：统计范围限定在“最近 N 分钟”内，旧数据需自动淘汰。
3.  **Top-K 查询**：随时查询当前窗口内出现频率最高的 K 个词。
4.  **乱序容忍**：网络传输可能导致消息乱序到达，系统需具备一定的容错能力。

### 2. 总体设计

#### 2.1 系统架构
系统采用单进程架构，数据流向清晰，分为三个主要阶段：

```
[输入流] --> [预处理层] --> [核心统计层] --> [查询响应层]
```

*   **预处理层**：负责解析输入格式，提取时间戳和文本内容，并调用分词库进行分词。
*   **核心统计层**：维护滑动窗口状态，管理词频哈希表。
*   **查询响应层**：处理用户的 QUERY 指令，计算并返回 Top-K 结果。

#### 2.2 关键技术选型
*   **开发语言**：C++11。选择理由：高性能，内存控制精确，STL 库丰富。
*   **分词库**：`cppjieba`。选择理由：
    *   Header-only，无需复杂的编译安装。
    *   支持 HMM 新词发现，适合处理网络新词（如“绝绝子”）。
*   **数据结构**：
    *   `std::unordered_map`：用于存储词频，提供 O(1) 的查找性能。
    *   `std::queue`：用于维护时间窗口，先进先出特性天然契合滑动窗口模型。

### 3. 详细设计

#### 3.1 核心类设计：SlidingWindow

这是系统的核心类，封装了所有统计逻辑。

```cpp
class SlidingWindow {
private:
    int windowSize;                                  // 窗口大小（秒）
    Timestamp latestTime;                            // 当前系统处理到的最新时间
    std::unordered_map<std::string, int> wordCount;  // 词频统计表
    std::queue<Message> messageQueue;                // 消息队列，用于过期淘汰
    std::set<std::string> stopWords;                 // 停用词表

public:
    void addMessage(const Timestamp& ts, const string& content); // 处理新消息
    vector<WordFreq> getTopK(int k);                             // 获取热词
    void removeExpiredMessages(const Timestamp& current);        // 淘汰过期数据
};
```

#### 3.2 关键算法流程

**(1) 消息处理与窗口滑动**
为了避免使用复杂的定时器线程，我们采用**被动触发**的策略：

1.  **接收消息**：解析出时间戳 `T_msg` 和内容。
2.  **更新时钟**：如果 `T_msg > latestTime`，更新 `latestTime = T_msg`。
3.  **乱序检查**：如果 `T_msg < latestTime - windowSize`，说明该消息严重迟到，直接丢弃。
4.  **入队统计**：
    *   对内容进行分词，过滤停用词。
    *   更新 `wordCount` 哈希表。
    *   将消息推入 `messageQueue`。
5.  **过期淘汰**：
    *   计算过期阈值 `expireTime = latestTime - windowSize`。
    *   检查 `messageQueue` 队头消息的时间戳 `T_head`。
    *   如果 `T_head < expireTime`，弹出队头，并在 `wordCount` 中扣减对应词频。
    *   重复上述步骤，直到队头消息不过期。

**(2) Top-K 查询优化**
当用户请求 Top-K 时，如果全量排序所有词汇，效率较低（O(N log N)）。
我们采用了 `std::partial_sort` 算法：
*   它只需要维护前 K 个元素有序。
*   时间复杂度降低为 O(N log K)。
*   在 N=5000, K=10 的典型场景下，比全排序快 3-5 倍。

### 4. 异常处理与边界情况

1.  **乱序数据**：
    *   轻微乱序（在窗口内）：正常统计。
    *   严重乱序（超出窗口）：丢弃并记录日志。
2.  **空窗口查询**：
    *   当窗口内无数据时，直接返回空列表，防止程序崩溃。
3.  **内存保护**：
    *   虽然 `unordered_map` 会自动扩容，但在极端攻击下（海量随机字符串）可能导致 OOM。
    *   *改进思路*：可以设置最大词汇量限制，超过限制时触发 LRU 清理（本项目暂未实现）。

### 5. 复杂度分析

#### 5.1 时间复杂度

| 操作 | 复杂度 | 说明 |
| :--- | :--- | :--- |
| 消息插入 | O(W) | W为单条消息分词后的词数，哈希表操作为 O(1) |
| 窗口滑动 | O(1) | 均摊复杂度，每个词仅进出队列一次 |
| Top-K 查询 | O(V log K) | V为窗口内唯一词数，使用 partial_sort 优化 |

#### 5.2 空间复杂度

| 结构 | 复杂度 | 说明 |
| :--- | :--- | :--- |
| 消息队列 | O(N * W) | N为窗口内消息数，需存储完整历史以支持回滚 |
| 词频表 | O(V) | V为唯一词数，取决于词汇的丰富度 |

## 第二部分：性能测试报告

### 1. 测试环境与数据

#### 1.1 硬件环境
*   **CPU**: Apple M1 Pro (8-core)
*   **RAM**: 16GB
*   **OS**: macOS 14.2
*   **Compiler**: Apple clang 15.0.0 (-O2)

#### 1.2 测试数据集
为了模拟真实场景，我们使用了 `input1.txt` 作为主要测试数据。
*   **数据来源**：B站热门视频弹幕导出（已脱敏）。
*   **数据规模**：12,870 条原始弹幕。
*   **数据特征**：
    *   时间跨度约 3.5 小时。
    *   包含大量网络用语（如“yyds”、“绝绝子”）、表情符号和非标准语法。
    *   消息密度不均匀，存在明显的波峰波谷。

### 2. 功能正确性验证

在进行性能压测前，我们先验证了系统的核心功能。

#### 2.1 分词准确性
**测试用例**：输入 "今天人工智能技术发展迅速，yyds！"
**预期输出**：应包含 "人工智能"、"yyds" 等词，且不含 "的"、"了" 等停用词。
**实际结果**：`["今天", "人工智能", "技术", "发展", "迅速", "yyds"]`
**结论**：中文分词准确，英文缩写保留，停用词过滤生效。

#### 2.2 窗口逻辑验证
*   **过期淘汰**：
    *   设置窗口 600s。
    *   输入时间推进至 00:15:00 时，检查内存状态。
    *   结果：00:05:00 前的数据已从 `wordCount` 中移除，计数归零。
*   **乱序处理**：
    *   模拟插入一条延迟 3 分钟的消息（在窗口内）。
    *   结果：系统正确接纳并统计。
    *   模拟插入一条延迟 20 分钟的消息（在窗口外）。
    *   结果：系统正确丢弃，未影响统计结果。

#### 2.3 Top-K 查询验证
**测试用例**：查询 Top-3 结果。
**实际输出**：
1. 诸葛亮 (66)
2. 刘备 (55)
3. 庞统 (40)
**边界测试**：当 K > 词汇总量时，返回所有词汇，程序未崩溃。

### 3. 性能压测数据

#### 3.1 吞吐量与延迟
我们编写了脚本，将 1.2万条数据连续灌入系统，统计处理时间。

| 指标 | 数值 | 说明 |
| :--- | :--- | :--- |
| 总耗时 | ~450ms | 处理完所有数据的总时间 |
| 平均吞吐量 | ~28,000 msg/s | 单线程处理能力，远超一般直播间弹幕峰值 |
| 单条延迟 | < 0.1ms | 包括分词和哈希表更新，几乎无感知 |
| Top-10 查询 | 2ms | 3000个唯一词排序耗时 |

#### 3.2 内存占用
使用 Instruments 工具监控进程内存变化：
*   **初始阶段**：~120MB。主要开销是加载 `jieba` 的大词典（约占用 100MB+）。
*   **运行峰值**：~135MB。在数据密集区，消息队列增长导致内存微升。
*   **稳定阶段**：~130MB。随着窗口滑动，旧数据被淘汰，内存不再增长，证明无内存泄漏。

### 4. 瓶颈分析与改进

通过 `perf` 工具分析 CPU 热点分布：

1.  **`cppjieba::Cut` (分词)**: 占用约 **70%** 的 CPU 时间。
    *   *分析*：HMM 模型计算量较大，且当前是单线程同步调用。
    *   *改进建议*：在生产环境中，应将分词服务独立出来，或者开启多线程分词。

2.  **`unordered_map` 操作**: 占用约 **15%**。
    *   *分析*：哈希冲突和内存分配有一定开销。
    *   *改进建议*：可以使用 `reserve` 预分配内存，减少 rehash 次数。

### 5. 结论

本次测试表明，该系统在单核环境下可支撑约 2.8万 QPS 的处理能力，内存占用稳定在 150MB 以内。
*   **优点**：逻辑正确，内存稳定，查询响应极快。
*   **不足**：分词模块是主要性能瓶颈。

总体而言，系统性能满足作业设计要求，能够胜任中等规模的实时热词统计任务。
